## 2. 产品定位与项目集

本项目围绕三个产品能力建设，并使用一个统一的 Agent 运行语义：

1. **Spring Boot 企业应用脚手架**：提供可组合的 Web、数据、权限、配置、任务、监控和运维能力。参考若依的企业后台组织方式与 CRUD 生成体验，自主设计本项目的模块、契约和源码。
2. **AI Agent 快速搭建框架**：按配置装配 LangGraph Runtime、模型、Prompt、Tool、Skill、MCP、RAG、短期与长期记忆、多 Agent、策略门和评测。
3. **低代码源码开发平台**：开发者在本项目的平台管理端配置模块、数据模型、表单、权限和完整 Agent 执行链；Agent 画板是其中一个开发模块。平台校验并生成可维护、可独立运行的 Java / Python / Web 源码。

三个能力共享统一执行核心：可视化配置先转换为版本化 Canonical Workflow IR，再由 LangGraph Runtime 执行或导出源码。Java 业务事务仍由 Spring Boot 负责。

项目集由自主实现的脚手架平台、可复用的 Spring Boot / Agent 组件包、生成器模板，以及生成的独立应用组成。**HR 工作台是脚手架的首个完整业务应用与验收样例，脚手架本体不是 HR 工作台。** 已先行生成非 HR 的 Asset 小样，检验单实体生成器的通用性；它不是完整业务成品。后续可生成客服、法务、运维等应用。每个应用必须通过平台公开契约生成，不能把场景逻辑写死到平台核心。

若依仅是产品设计理念的参考：借鉴其系统管理、模块目录、表单与代码生成的开发体验。`Yuan_Scaffold` 是独立项目，**不是若依仓库的 Fork，也不以若依源码为二次开发基座**。技术实现、数据契约、模板、升级和许可证均由本项目独立确定。

“Spring Boot 的所有功能”在本项目中是**持续扩展的能力覆盖目标**：用 Starter / 模板 / 适配器目录覆盖常见企业应用能力，并为未覆盖能力提供可注册扩展点。任何版本只声明已经实现和验证的模块，不能因为依赖 Spring Boot 就宣称全部能力已交付。

HR 工作台是首个完整业务验收载体。开发平台的导航、权限管理、字典配置、代码生成、模块装配和运维形式参考若依；画板、RAG Lab 和 Agent 组件作为扩展开发能力接入同一平台。后续生成其他业务应用时，平台模块和运行契约应保持稳定。

### 3.1 开发平台管理端与 Agent Studio

- 平台管理端提供系统管理、模块目录、数据模型、表单、菜单权限、代码生成预览、任务监控和版本发布；Agent Studio 是平台中的可选开发模块，不是平台整体形态。
- React Flow 只负责节点、边、表单、画布状态、调试结果与可视化，不在浏览器里执行可信业务逻辑。
- 保存的是可版本化的 Workflow IR，不直接把 React Flow 的 UI JSON 当成生产运行契约。
- 提供工作流编辑器、模块选择器、RAG 数据健康面板、评测对比、发布与源码导出。
- 前端可以高度定制。脚手架生成业务 API 客户端和页面骨架，但不强迫成品沿用固定管理后台视觉。

### 3.2 Java Control Plane

- 负责可信身份、租户、用户、组织、权限、策略、审计和业务事务。
- 负责 Agent、Workflow、Prompt、Provider、Knowledge Base、Tool、Skill、Eval Set 和 Release Catalog。
- 负责模块选择、Manifest 校验、模板渲染、差异预览、构建验证和生成物登记。
- 负责调用 Python Runtime，但不把模型建议当作权限或业务事务的最终决定。
- 默认先做模块化单体；边界稳定并有独立伸缩需求后，才抽取微服务。

### 3.3 Python Agent Plane

- LangGraph 是工作流、Agent Loop、Router、Checkpoint、interrupt、resume 和 Multi-Agent 的唯一执行核心。
- FastAPI 只提供运行协议和内部 API，不承担 Java 业务系统的权威身份与交易状态。
- Model Gateway、RAG、Memory、Tool Adapter、评测和 Trace 都以 LangGraph run 为中心串联。
- 支持平台托管执行与源码导出执行，两种方式使用同一 Workflow IR 和行为契约。

### 3.4 Generated Application

- 生成物必须是可以独立构建、运行、测试和部署的源码工程。
- Java 业务代码、Python LangGraph 代码、前端 SDK / 页面骨架都允许开发者继续修改。
- 生成物不依赖脚手架平台在线存活才能运行；平台只在继续编辑、发布或同步时提供增量能力。
- 每次生成都记录模板版本、模块清单、IR 版本和迁移信息，支持升级与差异合并。

## 4. 六条完整链路

### 4.1 项目生成链

```text
选择架构（模块化单体 / 微服务目标）
  -> 选择基础模块与可选模块
  -> 配置数据模型 / 表单 / 菜单 / 权限 / API / Agent 工作流
  -> 填写项目 Manifest、生成目标和技术栈版本
  -> 依赖、命名、Schema、权限和模板兼容性校验
  -> 生成 Java / Python / Web 临时工程
  -> 格式化、静态检查、编译和契约测试
  -> 展示文件清单与差异
  -> 用户确认导出
  -> 记录模板、模块和生成版本
```

生成器属于开发工具，不进入生产应用的运行依赖。低代码表单和画板产出的是可审查的源码与配置，允许继续手写修改。任何模板生成失败都应保留日志与临时结果，不能把半成品登记为成功版本。重新生成时先计算差异、识别用户修改和冲突，不静默覆盖业务源码。

### 4.2 可视化工作流链

```text
React Flow 节点与连线
  -> UI Graph Draft
  -> Canonical Workflow IR
  -> Schema / 类型 / 图结构 / 权限 / 预算静态校验
  -> 编译为 LangGraph GraphSpec
  -> 沙箱测试与逐节点 Trace
  -> Golden Cases / RAG / Agent 评测
  -> 审批并发布不可变 Workflow Version
  -> 平台托管运行 或 导出 LangGraph 源码工程
```

画布不是运行时。前端不能通过隐藏节点、修改 ID 或伪造租户字段绕过服务端校验。

### 4.3 在线请求链

```text
用户请求
  -> Java API 认证与租户解析
  -> AuthZ / thread ACL / rate limit
  -> 生成可信 RuntimeContext 与 CapabilityGrant
  -> Python LangGraph 载入已激活 Workflow Version
  -> Router / Agent / RAG / Memory / Tool
  -> Java 对高风险 Tool 再授权并执行业务事务
  -> Answer Gate / Citation / Artifact
  -> Java 持久化业务状态、审计和用户可见结果
  -> Trace / Metric / Feedback
```

模型只能建议下一动作。是否执行、继续、重试、人工确认或终止，由 LangGraph 编排器和确定性策略共同决定。

### 4.4 知识摄取与索引发布链

```text
G0 Source Admission
  -> Parser / OCR / Adapter
  -> MetadataClaim + Evidence
  -> G1 Parse Quality
  -> Deterministic Normalization
  -> Trust Resolver
  -> G2 Canonical Schema
  -> G3 Business + Security Policy
  -> CanonicalDocument
  -> Chunk Strategy Router
  -> G4 Chunk Quality
  -> Embedding + Candidate Index
  -> Offline Evaluation
  -> G5 Index Admission
  -> Blue/Green Publish + Rollback Retention
```

六道质量门是标准组件。租户可调整被允许的阈值或添加沙箱规则，但身份、ACL、血缘、资源限制和发布完整性等安全规则不能被关闭。

### 4.5 在线 RAG 回答链

```text
Query
  -> intent / query resolution
  -> optional rewrite / decomposition
  -> tenant + KB + ACL + active-version prefilter
  -> sparse + dense retrieval
  -> RRF / fusion
  -> rerank
  -> retrieval confidence gate
  -> context budget + citation assembly
  -> model generation
  -> groundedness / citation / policy answer gate
  -> answer, abstain, clarify or human escalation
```

低分不等于事实置信度。回答是否发布，需要结合检索覆盖、证据支持、问题风险和答案忠实度判定。

### 4.6 评测、调优与发布链

```text
版本化数据集 + qrels / Golden Cases
  -> 固定代码、模型、Prompt、数据和索引版本
  -> 批量运行
  -> Recall@K / Precision@K / MRR / nDCG
  -> groundedness / citation / task success / safety
  -> P50/P95、吞吐、Token、费用、内存和索引体积
  -> 候选配置比较
  -> 发布门审批
  -> 灰度、监控、回滚
```

HNSW 中 `M` 和 `efConstruction` 需要构建候选索引后比较；`efSearch` 可以作为查询期参数实验。任何调参结论都必须绑定数据集、Embedding、距离度量、过滤条件和硬件环境。

## 5. React Flow 节点体系

React Flow 只渲染和编辑以下节点。每个节点的真实执行器位于 Java 或 Python 后端，并通过注册表绑定。

| 节点族 | 典型节点 | 执行位置 | 是否调用模型 |
| --- | --- | --- | --- |
| `flow.*` | Start、End、Branch、Loop、Parallel、Join | LangGraph | 否 |
| `agent.*` | ReAct、Router、Planner、Evaluator、SubAgent | LangGraph | 通常是 |
| `text.*` | Normalize、Regex Extract、Token Split、Recursive Split、Metadata Map | Python Worker | 否 |
| `nlp.*` | Intent Classifier、NER、Semantic Chunker、Query Rewrite、Summarizer | Python Provider Adapter | 明确标注 |
| `rag.*` | Parse、Quality Gate、Embed、Retrieve、RRF、Rerank、Context、Citation | Python RAG Runtime | 部分调用 |
| `tool.*` | Java Service、OpenAPI、MCP、Local Function、Agent-as-Tool | Java / Python | 不一定 |
| `memory.*` | Checkpoint、Semantic、Episodic、Procedural | LangGraph + Store | 部分调用 |
| `policy.*` | AuthZ、Budget、Risk、Approval、Content Gate | Java / LangGraph | 授权判断不调用模型 |
| `human.*` | Review、Approve、Reject、Edit | Java Control Plane | 否 |
| `io.*` | Chat Input、File Input、Answer、Artifact、Webhook | Java / Web | 否 |

“NLP”不得成为含义模糊的大分类。界面必须显示该节点是：

- 确定性规则；
- 本地 NLP 模型；
- Embedding / Rerank 模型；
- 生成式 LLM；
- 外部 API。

用户据此判断费用、延迟、可重复性、隐私和失败语义。

## 6. Workflow IR 与编译边界

### 6.1 最小 Workflow IR

每个工作流版本至少包含：

- `workflow_id`、`version`、`schema_version`、`status`；
- `nodes[]`、`edges[]`、入口和允许的终点；
- 节点类型与节点实现版本；
- 节点参数与配置 Schema，包括检索分段 TopK、模型与预算设置；
- 输入、输出和状态 Schema；
- timeout、retry、idempotency、budget 和 fallback；
- 所需 Tool / Skill / Model / KB / Memory Binding，以及索引 / RAG 配置版本；
- 风险等级、审批要求和 Capability；
- 测试集、评测阈值和发布证据；
- 生成器与模板版本。

React Flow 的坐标、折叠状态和颜色属于 `ui_metadata`，不得影响工作流执行语义。

### 6.2 编译流水线

```text
ReactFlowGraph
  -> parse
  -> canonicalize IDs and ports
  -> validate schemas and edge compatibility
  -> detect unreachable nodes / illegal cycles
  -> validate capabilities and release bindings
  -> build LangGraph GraphSpec
  -> generate Python package
  -> format + type-check + unit/contract tests
  -> produce source archive and manifest
```

第一版优先使用模板 + AST / 结构化模型生成，不使用字符串拼接生成任意 Python。循环节点必须带预算和停止条件；副作用节点必须带幂等与审批策略。

### 7.2 可选平台模块

### 7.6 MCP Scale 运行边界

**MCP Scale 是本项目对“多 MCP 服务规模化接入与治理”的模块名称，不是 MCP 协议中的标准组件。** 每个服务登记 `server_id`、协议版本、transport、工具 / 资源 / 提示能力、输入输出 Schema、owner、租户可见范围、凭据引用、风险和健康状态。平台支持本地 stdio 与远程 Streamable HTTP 适配，并按协议版本隔离兼容行为。

请求经 `Agent / Skill Binding -> Capability Grant -> MCP Catalog / Router -> 输入 Schema -> 风险 / 策略 / 预执行 / 必要审批 -> transport client -> 输出 Schema 与结果规范化 -> Tool Execution Audit`。拒绝与失败也进入审计，实际 `tools/call` 必须发生在授权和审批之后。连接池、并发限额、超时、熔断、背压、配额、健康探测和水平扩展由服务端治理；服务不可用、版本不兼容或授权不明确时给出显式失败或受控降级。远程凭据仅在执行边界解析，不能进入 Prompt、画板 JSON 或生成物明文。

## 9. RAG 质量治理与可视化调优

### 9.1 六道标准质量门

| 质量门 | 核心检查 | 主要输出 |
| --- | --- | --- |
| G0 Source Admission | 身份、租户、KB 写权限、文件类型、大小、MIME / 签名、恶意文件、配额 | 接收或拒绝及审计 |
| G1 Parse Quality | 空文档、乱码、OCR、页覆盖、表格、图片、截断、解析诊断 | ParsedDocument 或隔离 |
| G2 Canonical Schema | 字段类型、日期、来源、Evidence、版本、必填字段 | CanonicalMetadata |
| G3 Business & Security Policy | 生效时间、版本关系、发布状态、ACL、数据分级 | Policy Admission |
| G4 Chunk Quality | 长度、覆盖、重复、孤立标题、表格、血缘、Chunk ID 与 ACL | 可索引 Chunks |
| G5 Index Admission | 向量维度、数量、失败率、抽样召回、Manifest、ACL 对齐、容量 | 可发布 Index Version |

每道门统一返回 `ACCEPT / WARN / QUARANTINE / REJECT`、规则版本、证据、修复建议和审计关联 ID。`ACCEPT` 是摄取准入结果；测试执行的通过 / 失败另用 `PASS / FAIL`，不复用准入字段。

### 9.2 RAG Lab

RAG Lab 至少展示：

- 文档、页、元素、Chunk、Embedding 和 Index 的血缘；
- 每道质量门的通过、告警、隔离和拒绝分布；
- Chunk 长度、重叠、重复率、标题覆盖、表格 / 图片覆盖；
- 查询级候选、Sparse / Dense 分数、RRF 顺序、Rerank 顺序和最终引用；
- Recall@K、Precision@K、MRR、nDCG、忠实度和引用支持率；
- HNSW `M`、`efConstruction`、`efSearch` 对质量、P95、内存、构建时间和索引体积的影响；
- 基线与候选版本差异、发布门和一键回滚目标。

### 9.3 检索与 ANN 参数实验

RAG Lab 提供分阶段的 `dense_top_k`、`sparse_top_k`、`fusion_top_k`、`rerank_top_k`、`context_top_k` 配置，并显示各阶段实际候选数量、ACL 过滤数量、截断原因与最终引用。`TopK` 是查询与上下文装配配置；后端可用范围、候选上限和 `rerank_top_k <= fusion_top_k` 等约束由具体检索适配器验证。不能把 Recall@K 的评测 K 与运行时 TopK 混为同一个字段。

HNSW 的 `M` 与 `efConstruction` 属于**索引构建配置**。修改它们必须生成新的候选索引版本，完成构建、完整性检查和评测后再切换；`efSearch`（不同后端也称查询期 `ef`）属于**查询配置**。平台按具体向量后端及版本展示合法范围，并在后端要求时校验查询期 `efSearch >= dense_top_k`，不硬编码跨后端通用值。候选实验固定文档集、Embedding、距离度量、过滤条件和硬件，再对比：

1. ANN Recall@K：与相同过滤条件下的精确检索结果比较，定位索引近似误差。
2. 检索相关性：用 qrels 测 Recall@K、Precision@K、MRR、nDCG，区分切分、过滤、召回、融合和重排影响。
3. 最终答案：测忠实度、引用支持率、任务成功、安全拒绝，以及 P50 / P95、吞吐、成本、内存、索引体积和构建耗时。

每次实验保存数据集、配置快照、代码 / 模型 / Prompt / Chunking / Index 版本、结果与差异。被选中的分段 TopK 和查询期参数进入版本化 RAG 配置并由 Workflow IR 引用，构建期参数进入 Index Manifest；源码导出时保留这些引用与可解析的配置快照。发布门只接受可复现的候选版本；回滚不得重新暴露已删除或撤权内容。

## 10. 首个完整业务验收应用：HR 工作台

本节定义第一次使用脚手架完成的完整业务验收应用，不规定脚手架平台的页面形态。现有 Asset 应用只是先行的非 HR 单实体生成样例。平台本体以第 2、3、7.4 节的独立开发框架、模块目录和代码生成器为准。

### 10.1 用户场景

首个 HR 应用必须完成以下真实闭环：

1. 员工询问政策，系统返回带版本和引用的答案。
2. 员工查询本人假期余额，权限只允许读取本人数据。
3. 员工发起请假，Agent 收集缺失信息，Java 业务服务校验并创建申请。
4. 高风险或不完整申请进入人工审批；恢复后从 Checkpoint 继续。
5. 主管审批后，系统更新权威业务状态并向员工返回可核对结果。
6. HR 管理员上传新政策，经 G0-G5、评测、审批和蓝绿发布后生效。
7. Supervisor 可将政策、薪酬、考勤等专业任务交给最小权限子 Agent，再合成结果。
8. 每个答案、Tool 调用、审批和索引版本都能从 Trace 还原。

### 10.2 成品交付件

- 可独立运行的 Java 后端；
- 可独立运行的 Python LangGraph Runtime；
- 可定制的员工端与管理端前端；
- 数据库迁移和初始化 Fixture；
- HR Workflow IR 与导出的 LangGraph 源码；
- RAG 评测集、Golden Cases 与基线报告；
- 安全、隔离、恢复、发布和回滚测试；
- 本地开发、部署、升级和故障处理文档。

### 10.3 “成品”验收标准

只有以下全部满足，HR 才能称为脚手架生成的最终成品：

- 生成后脱离平台仍可构建和运行；
- 可在源码中修改业务规则与页面并重新发布；
- Java、Python、Web 跨语言契约测试通过；
- 正向业务、越权负向、失败恢复、幂等和审计测试通过；
- RAG 质量与性能达到项目预先登记的阈值；
- Workflow、Prompt、Tool、Knowledge、Index 和生成模板可版本化与回滚；
- 使用同一脚手架生成一个受控的非 HR 小样，证明核心没有写死 HR。

## 11. 能力阶段与主版本覆盖矩阵

采用**螺旋式迭代、逐版扩大的最小闭环**：每个主版本先登记目标和关键风险，再实现可复现验证、观察结果、决定修订或回退的纵向切片；下一版在其上增加能力并重跑关键回归。v0.1 的闭环是契约校验；从 v0.2 起验证实际运行。S0-S13 是能力阶段与完成门，不是要求前一阶段全部完成后才启动下一阶段的瀑布计划；例如简化代码生成先在 v0.3 形成闭环，S10 再完成多技术栈生成与升级治理。

## 13. 跨模块硬性不变量

1. `tenant_id`、用户身份、ACL、审批和资源绑定只来自可信服务端上下文。
2. LLM 可以建议动作，不能签发权限、权威 ID、业务成功状态或发布批准。
3. React Flow UI JSON 不能直接成为生产执行输入；必须经过 Canonical IR 和服务端校验。
4. 所有循环都有步数、Token、费用、时间和工具调用预算。
5. 所有副作用都有幂等键、预执行、风险门、必要人工确认和审计。
6. Document、Chunk、Embedding、Index、Citation、Memory 和 Artifact 保持租户、版本和血缘。
7. 安全字段缺失或冲突时 fail closed。
8. 标记为可运行、可交付的生成源码必须经过格式化、编译、类型检查和契约测试；预览和未经逐配置构建验证的草稿 ZIP 必须显式标注状态，不能算作已通过正式导出门。
9. Fake / Stub 只能用于测试，生产路径不得返回假成功。
10. 模型、Prompt、Workflow、Tool、Skill、Knowledge、Index、Schema 和模板均可版本化、评测和回滚。
11. 本仓库的“设计完成”不能被表述为“功能已实现”。
12. HR 生成应用只能依赖平台公开契约，核心平台不能反向依赖 HR 包。
